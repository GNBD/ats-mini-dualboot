## 0. 프로젝트 목표

사용자는 C 코드를 작성하지 않고도 GNBD ATS Mini 펌웨어의 동작을 시각적으로 설계하고, 결과물을 ESP32-S3 N16R8용 펌웨어로 빌드할 수 있어야 한다.

핵심 경험:
1. 사용자가 이벤트(Event), 조건(Condition), 동작(Action) 블록을 배치·연결한다.
2. 편집기는 블록 구조와 연결을 프로젝트 파일(JSON 등)로 저장한다.
3. 검증기는 잘못된 연결, 자료형 오류, 지원하지 않는 기능, 누락된 입력, 위험한 실행 흐름을 검사한다.
4. 코드 생성기는 검증된 프로젝트만 제한된 C 코드를 생성한다.
5. 생성된 코드는 기존 GNBD ATS Mini 펌웨어의 **명시적으로 노출된 안전한 API**만 호출한다.
6. 기존 프로젝트의 빌드 체계로 펌웨어를 컴파일하고 결과를 사용자에게 제공한다.
7. 사용자는 프로젝트를 저장·복제·공유하고 나중에 다시 열어 편집할 수 있다.

제품 정체성:
- 일반 설정 편집기만이 아니다.
- 임의의 C 코드를 생성하거나 실행하는 무제한 IDE도 아니다.
- 목표는 “ATS Mini용 비주얼 펌웨어 프로그래밍 환경”이다.
- 앱인벤터에서 영감을 얻되, 앱인벤터 전체를 재현하려 하지 않는다.
- 초기 버전은 정적 C 코드 생성 방식으로 구현한다. ESP32에서 범용 블록 인터프리터를 실행하는 방식은 1단계 범위에서 제외한다.

## 1. 에이전트 작업 규칙 — 반드시 준수

- [ ] 작업 전 현재 저장소의 구조, 기술 스택, 빌드 절차, 대상 보드, 라이선스와 기존 코드를 조사한다.
- [ ] 이미 구현된 기능을 다시 만들지 않는다. 먼저 검색·실행·테스트한다.
- [ ] 기존 동작을 깨는 광범위한 리팩터링을 피한다.
- [ ] 기존 펌웨어의 라디오 제어·UI·입력 처리 코드를 충분히 읽기 전에는 API를 임의로 가정하지 않는다.
- [ ] 함수명, 파일명, 프레임워크, 빌드 명령을 추측해서 만들지 않는다. 확인되지 않은 것은 TODO/미확인으로 기록한다.
- [ ] 처음부터 모든 기능을 만들지 않는다. 각 단계가 빌드·테스트되는 작은 변경으로 나눈다.

- [ ] 기존 파일을 덮어쓰기 전 변경 사항을 확인한다. 사용자 변경을 보존한다.
- [ ] 새 의존성을 추가하기 전에 현재 라이브러리와 라이선스를 확인하고 추가 이유를 설명한다.

- [ ] 블록 프로젝트는 입력 파일로 간주한다. 잘못되거나 악의적인 JSON을 파싱해도 앱이 충돌하거나 임의 코드가 실행되지 않아야 한다.
- [ ] 사용자에게 확인이 필요한 아키텍처 결정은 한 번에 하나씩 명확한 선택지를 제시한다. 확인되지 않은 가정으로 큰 구현을 시작하지 않는다.
- [ ] 저장소를 조사한 후 이 문서의 항목을 실제 경로와 구조에 맞게 갱신한다.
- [ ] 모든 TODO에 완료 기준과 테스트를 연결한다.
- [ ] UI가 존재한다는 사실만으로 기능 완료라고 판단하지 않는다. 실제 생성 코드와 실제 빌드까지 확인한다.

## 5. 프로젝트 파일 / JSON 스키마

초기 예시일 뿐이며, 실제 구현 전 스키마를 명시적으로 정의하고 검증해야 한다.

```json
{
  "format": "gnbd-mod-project",
  "schemaVersion": 1,
  "project": {
    "id": "example-project",
    "name": "RSSI Scan Stop",
    "description": "Stop scanning when a signal crosses a threshold"
  },
  "target": {
    "board": "ESP32-S3-N16R8",
    "firmware": "GNBD ATS Mini"
  },
  "blocks": [
    {
      "id": "event-1",
      "type": "event.rssi_updated",
      "position": {"x": 100, "y": 100},
      "inputs": {}
    },
    {
      "id": "condition-1",
      "type": "logic.compare",
      "position": {"x": 100, "y": 220},
      "inputs": {
        "left": {"kind": "value", "value": {"type": "radio.rssi"}},
        "operator": ">=",
        "right": {"kind": "literal", "value": 30}
      }
    }
  ],
  "connections": [
    {"from": {"blockId": "event-1", "port": "next"}, "to": {"blockId": "condition-1", "port": "previous"}}
  ],
  "settings": {
    "maxTimers": 4
  }
}
```

주의:
- 이 예시는 개념 예시이며, 실제 블록 모델에 맞게 확정해야 한다.
- 프로젝트 JSON에 실행 가능한 C 코드나 임의 명령을 넣지 않는다.
- 모든 `type`, `operator`, `port`, `input`은 허용된 값인지 검증한다.
- 숫자 범위, 문자열 길이, 블록 수, 연결 수, 중첩 깊이를 제한한다.
- 중복 블록 ID, 존재하지 않는 연결 대상, 연결 순환(허용되지 않는 경우), 끊긴 입력을 검사한다.
- JSON 스키마 버전이 다르면 명시적으로 오류 또는 마이그레이션 처리한다.
- 프로젝트 저장 형식은 UI 좌표와 실행 의미를 분리할 수 있도록 설계한다.

## 6. 블록 스펙: MVP

처음부터 많은 블록을 만들지 말고 실제 API가 확인된 블록만 노출한다. 아래 목록은 후보이며, 저장소 조사 후 사용 가능한 항목만 확정한다.

### 6.1 이벤트 블록 후보
- [ ] `event.boot_ready` — 펌웨어 초기화 완료
- [ ] `event.frequency_changed` — 주파수 변경
- [ ] `event.rssi_updated` — RSSI 값 갱신
- [ ] `event.scan_started` — 스캔 시작
- [ ] `event.scan_finished` — 스캔 종료
- [ ] `event.button_pressed` — 특정 버튼/엔코더 입력
- [ ] `event.timer_tick` — 등록된 주기 타이머
- [ ] 각 이벤트의 호출 주체/빈도/실행 컨텍스트 문서화
- [ ] 이벤트 콜백에서 오래 걸리는 작업을 금지하거나 지연 작업 큐로 넘긴다.

### 6.2 조건/논리 블록 후보
- [ ] 숫자 비교: `==`, `!=`, `<`, `<=`, `>`, `>=`
- [ ] 논리: AND, OR, NOT
- [ ] 라디오 상태 확인: 현재 모드/스캔 상태
- [ ] 범위 검사
- [ ] 타이머 경과 시간 검사
- [ ] 사용자 변수 비교
- [ ] 조건의 자료형 일치 검사
- [ ] 부동소수점/정수 비교 정책 정의

### 6.3 값/변수 블록 후보
- [ ] 상수: 정수, 제한된 실수, 참/거짓, 허용된 문자열
- [ ] 라디오 읽기 값: 주파수, RSSI, SNR, 수신 모드(실제 API 확인 후)
- [ ] 프로젝트 내 사용자 변수 선언
- [ ] 변수 읽기/쓰기
- [ ] 산술 연산: +, -, 최소한의 안전한 연산
- [ ] 0으로 나누기, 오버플로, 범위 초과 정책 정의
- [ ] 초기 버전에서 임의 배열/포인터/동적 메모리 노출 금지

### 6.4 동작 블록 후보
- [ ] `action.show_message` — 화면에 짧은 메시지 표시
- [ ] `action.set_waterfall_visible` — 워터폴 표시 제어(가능한 API가 있을 때)
- [ ] `action.stop_scan` — 스캔 정지(기존 API가 있을 때)
- [ ] `action.start_scan` — 스캔 시작(기존 API가 있을 때)
- [ ] `action.save_frequency` — 주파수 저장(저장 정책 확인 후)
- [ ] `action.log_value` — 제한된 로그/이력 기록
- [ ] `action.set_user_variable` — 사용자 변수 변경
- [ ] `action.notify` — UI 알림
- [ ] 모든 동작은 결과/실패 가능성 및 실행 컨텍스트를 문서화한다.
- [ ] 하드웨어 제어는 UI 스레드/메인 루프와 충돌하지 않게 한다.

### 6.5 흐름 제어 후보
- [ ] IF/ELSE
- [ ] 제한된 횟수 반복 또는 반복 블록 없이 초기 MVP 구성
- [ ] 지연/타이머는 비차단 방식으로 구현
- [ ] 무한 반복 블록을 제공하지 않는다.
- [ ] 사용자 프로젝트가 펌웨어의 메인 루프를 막지 못하게 한다.
- [ ] 이벤트 중복 실행/재진입 정책을 명시한다.
- [ ] 타이머 수, 이벤트당 작업 수, 사용자 변수 수에 제한을 둔다.

## 7. API 경계 / 런타임 통합

- [ ] 블록 생성 전에 기존 펌웨어 코드에서 실제 함수/자료형을 확인한다.
- [ ] 사용자 정의 동작 전용 API 계층을 만든다. 이름은 저장소 스타일에 맞춘다.
- [ ] 생성 코드가 기존 내부 구현의 전역 변수에 직접 접근하지 않도록 한다.
- [ ] 읽기 API와 변경 API를 구분한다.
- [ ] 라디오 제어 API는 허용 목록으로 관리한다.
- [ ] API마다 입력 범위, 실행 시간, 호출 가능한 컨텍스트, 실패 조건을 문서화한다.
- [ ] 긴 작업은 이벤트 콜백에서 직접 실행하지 않는다.
- [ ] 라디오 드라이버/SI4732 통신을 임의로 동시에 호출하지 않는다.
- [ ] 화면/UI 업데이트는 기존 UI 소유권과 스레드 규칙을 따른다.
- [ ] NVS 쓰기는 빈번한 이벤트마다 수행하지 않도록 제한/버퍼링한다.
- [ ] 사용자 기능이 기본 수신/오디오/입력 처리를 막지 않도록 한다.
- [ ] 사용자 동작에 실행 시간/호출 빈도/메모리 제한을 적용한다.
- [ ] 오류 발생 시 기본 펌웨어 기능을 계속 사용할 수 있는 실패 정책을 정의한다.
- [ ] 사용자 정의 모듈이 비활성화되어도 기존 펌웨어가 빌드되도록 한다.

## 8. 검증기

- [ ] JSON 구문 검사
- [ ] 스키마 버전 검사
- [ ] 중복/누락 ID 검사
- [ ] 미지원 블록 타입 검사
- [ ] 잘못된 포트 연결 검사
- [ ] 필수 입력 누락 검사
- [ ] 자료형 불일치 검사
- [ ] 연결 그래프 순환 검사(허용된 루프 모델에 맞춰)
- [ ] 허용되지 않은 무한 실행 흐름 검사
- [ ] 리소스 제한 검사(블록 수, 타이머 수, 변수 수 등)
- [ ] API 의존성 검사
- [ ] 상호 배타적인 기능 조합 검사
- [ ] 사용자 문자열 길이/인코딩 검사
- [ ] 빌드 대상/보드 불일치 검사
- [ ] 파티션/펌웨어 크기 한계는 실제 빌드 결과와 기존 규칙에 따라 검사
- [ ] 오류는 `code`, `message`, `blockId`, `field`, `severity` 형태로 표현
- [ ] UI에서 오류를 클릭하면 해당 블록/필드로 이동
- [ ] 오류가 하나라도 있으면 코드 생성/빌드 실행을 막는다(명시적으로 허용한 경고 제외)

## 9. C 코드 생성기

- [ ] 프로젝트 모델을 직접 문자열 이어붙이기로 처리하지 말고 typed IR로 정규화한다.
- [ ] 블록 종류별 생성 템플릿/생성 함수를 명시적으로 등록한다.
- [ ] 허용된 블록 타입만 코드 생성 가능하다.
- [ ] 사용자 입력은 숫자 범위와 타입을 검증한 후 리터럴로 출력한다.
- [ ] 문자열은 C 문자열 리터럴로 안전하게 이스케이프한다.
- [ ] 임의 함수명, include, 전처리기 명령, C 구문을 프로젝트 입력으로 받지 않는다.
- [ ] 코드 생성 결과는 별도 generated 디렉터리에 저장한다.
- [ ] 생성 코드에 원본 프로젝트 블록 ID 또는 진단용 주석을 연결할 수 있게 한다.
- [ ] 생성된 코드에 수동 수정하지 말라는 안내를 둔다.
- [ ] 생성 결과를 deterministic하게 만든다(동일 프로젝트/버전이면 같은 출력).
- [ ] 코드 생성기 단위 테스트: 블록별 expected output 테스트
- [ ] 코드 생성기 통합 테스트: 샘플 프로젝트에서 컴파일 가능한 코드 생성
- [ ] 생성 코드에 임의 외부 명령이나 쉘 실행이 포함되지 않도록 한다.

## 10. 빌드 어댑터

- [ ] 현재 펌웨어 빌드 체계와 명령을 저장소에서 확인한다.
- [ ] 기존 빌드 환경을 재사용하고 새 빌드 시스템을 중복 도입하지 않는다.
- [ ] 빌드 호출을 UI 컴포넌트에 직접 넣지 않고 별도 어댑터로 분리한다.
- [ ] 프로젝트별 임시 빌드 디렉터리를 분리한다.
- [ ] 빌드 시작/진행/성공/실패 상태를 전달한다.
- [ ] stdout/stderr 또는 빌드 로그를 수집한다.
- [ ] 실패 로그를 사용자 친화적 오류로 표시하되 원문 로그도 제공한다.
- [ ] 빌드 취소 기능은 안전하게 프로세스를 정리할 수 있을 때만 구현한다.
- [ ] 동시 빌드 충돌을 방지한다.
- [ ] 이전 성공 BIN을 새 빌드 실패 때문에 삭제하지 않는다.
- [ ] 대상 보드 ESP32-S3 N16R8과 실제 PSRAM/Flash 설정을 유지한다.
- [ ] 파티션 테이블을 사용자 프로젝트가 임의로 변경하지 못하게 한다.
- [ ] BIN 크기 및 플래시 주소/파일 구성은 실제 빌드 산출물 기준으로 검증한다.
- [ ] 현재 앱 슬롯/파티션 크기 제약을 넘으면 명확하게 실패 처리한다.
- [ ] 결과 파일과 함께 빌드 리포트를 저장한다.
- [ ] GUI에서 실제 빌드가 불가능한 브라우저 환경이면, 지원되는 로컬 빌드 에이전트/CLI 구조를 별도 설계하고 사용자가 이를 설치해야 함을 명확히 표시한다. 브라우저가 임의로 로컬 컴파일러에 접근한다고 가정하지 않는다.

## 11. UI/UX

- [ ] 좌측: 블록 팔레트와 검색
- [ ] 중앙: 블록 작업 캔버스
- [ ] 우측: 선택 블록 속성 및 설명
- [ ] 하단: 검증 결과/빌드 로그/오류 목록
- [ ] 상단: 프로젝트 이름, 저장, 실행 검사, 빌드
- [ ] 블록마다 한국어 설명과 입력 범위 표시
- [ ] 연결 가능한 포트만 시각적으로 강조
- [ ] 잘못된 연결을 즉시 표시하되 편집기 전체를 멈추지 않는다.
- [ ] Undo/Redo는 블록 편집 MVP에 포함할지 구현 비용을 확인한 후 결정한다.
- [ ] 저장하지 않은 변경이 있을 때 표시한다.
- [ ] 프로젝트 불러오기 전에 형식과 크기를 검사한다.
- [ ] 캔버스 좌표는 실행 의미와 분리한다.
- [ ] 작은 화면보다 데스크톱 작업 환경을 우선 지원하되, 기존 앱 플랫폼을 조사한 후 결정한다.
- [ ] 접근성: 키보드 포커스, 명확한 오류 텍스트, 색상만으로 상태를 전달하지 않기
- [ ] 처음 사용하는 사용자를 위한 튜토리얼 프로젝트 제공
- [ ] 기능이 없는 버튼이나 동작하지 않는 메뉴를 만들지 않는다.

## 12. MVP 샘플 프로젝트

실제 API가 확인된 경우에만 아래 샘플을 활성화한다.

### 샘플 A: RSSI 임계값 감지
- [ ] 이벤트: RSSI 갱신
- [ ] 조건: RSSI가 사용자 지정 임계값 이상
- [ ] 동작: 화면 알림 표시
- [ ] 중복 알림 방지: 임계값 진입 에지 또는 쿨다운 사용
- [ ] 테스트: 임계값 아래/같음/위

### 샘플 B: 사용자 정의 엔코더 동작
- [ ] 이벤트: 엔코더 입력
- [ ] 조건: 입력 길게 누르기 또는 현재 기능 상태
- [ ] 동작: 워터폴 전환 또는 지원 가능한 다른 UI 기능
- [ ] 기본 조작과 충돌 여부 검사
- [ ] 테스트: 짧게 누르기, 길게 누르기, 빠른 연속 입력

### 샘플 C: 신호 약화 알림
- [ ] 타이머 또는 RSSI 이벤트 사용
- [ ] RSSI가 임계값 미만인 상태가 지정 시간 지속되는지 확인
- [ ] 조건 해제 시 타이머/상태 초기화
- [ ] 알림 반복 방지
- [ ] 테스트: 짧은 하락, 지속 하락, 신호 회복

### 샘플 프로젝트 공통
- [ ] 프로젝트 파일로 저장
- [ ] UI에서 편집 가능
- [ ] 검증기 통과
- [ ] C 코드 생성
- [ ] 펌웨어 빌드 성공
- [ ] 실제 ESP32-S3 N16R8에서 테스트
- [ ] 기본 FM/AM/SW/SSB 수신 및 UI에 회귀 문제가 없는지 확인

## 14. 성능 및 안전 제한

- [ ] 이벤트별 실행 빈도 상한 정의

- [ ] 타이머 최대 개수 정의
- [ ] 사용자 변수 최대 개수 정의
- [ ] 프로젝트 최대 크기 및 블록 수 정의

- [ ] 반복 알림/로그 쓰기 방지
- [ ] 런타임 오류 발생 시 해당 사용자 동작만 중단할 수 있는지 설계

- [ ] 프로젝트가 잘못되어도 기기를 부팅 불가 상태로 만들지 않는 설계
- [ ] 생성된 사용자 코드가 펌웨어 부팅/복구 경로를 수정하지 않도록 분리

## 17. 완료 정의 (Definition of Done)

다음 조건이 모두 충족되어야 MVP 완료로 선언한다.

- [ ] 사용자는 C 코드를 작성하지 않고 3개 샘플 중 적어도 하나를 편집할 수 있다.
- [ ] 프로젝트를 저장하고 다시 열 수 있다.
- [ ] 잘못된 연결은 빌드 전에 오류로 표시된다.
- [ ] 코드 생성기는 허용된 블록만 처리한다.
- [ ] 생성 코드가 기존 GNBD ATS Mini 소스와 통합되어 컴파일된다.
- [ ] ESP32-S3 N16R8용 펌웨어가 실제로 빌드된다.
- [ ] 적어도 한 개의 사용자 정의 동작이 실제 기기에서 작동한다.
- [ ] 기본 라디오 기능의 회귀 테스트가 통과한다.
- [ ] 빌드 실패 시 기존 소스와 이전 성공 산출물이 보존된다.
- [ ] 지원하지 않는 기능과 제한 사항이 문서화되어 있다.
- [ ] 테스트하지 않은 항목을 완료했다고 주장하지 않는다.

## 18. 에이전트에게 처음 내릴 작업 지시

**첫 번째 작업에서는 코드를 변경하지 말고 조사만 수행하라.**

1. 현재 툴 저장소의 디렉터리 구조, 기술 스택, UI 진입점, 테스트 명령을 조사한다.
2. GNBD ATS Mini 펌웨어 저장소의 실제 경로/버전/브랜치와 빌드 절차를 확인한다.
3. 기준 펌웨어를 빌드할 수 있으면 빌드하고 결과를 기록한다.
4. 이벤트, RSSI/SNR, 주파수, 엔코더, 스캔, 워터폴, UI 알림, 저장 기능의 실제 API와 구현 위치를 찾아 목록화한다.
5. 확인된 사실과 추측을 분리한다.
6. 이 TODO를 현재 프로젝트 구조에 맞게 보정하고, 우선순위·파일 경로·테스트 계획을 제안한다.
7. 조사 결과를 보고한 뒤, 가장 작은 end-to-end vertical slice(이벤트 1개 + 조건 1개 + 동작 1개 + 코드 생성 + 실제 빌드)를 구현한다.
8. 사용자 확인 없이 기존 펌웨어 전체를 재작성하거나 대규모 리팩터링하지 않는다.

**절대 하지 말 것:** 기존 코드를 제대로 읽지 않고 대량의 파일을 생성하는 것, 가상의 API를 사용하는 것, UI만 만들어 기능이 완성되었다고 말하는 것, 컴파일하지 않은 코드를 성공했다고 보고하는 것, 사용자 변경을 덮어쓰는 것.
